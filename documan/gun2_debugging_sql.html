SEKTÖREL BAKIŞ (Neden?)

Yavaş SQL ve laçka ayrıştırılmış bir stack, üretimde “saatler” kazandırır.

İş yükü yükselince, yanıt süresi artar; SQL ve ağ katmanı sistemin en büyük ayak sesini çıkarır. N+1 problemi yüzünden aynı tabloya defalarca SQL atıyorsanız, her istek birkaç yüz milisaniye daha çok kaybeder; 10.000 isteklik trafikte bu milyonlarca ek işlem haline gelir.

3–10xTemel eşiklerdeki artış; N+1 veya kötü sorgu planları çoğu zaman bunun nedeni olur.
p95SQL katmanında yükselen p95, görsel olarak “uygulama yavaş” algısı üretir.
TimeoutConnection pooling ve network latency kombinasyonunda elektronik “durdurucu” operasyon görünür.
⚠️ Dikkat: “Sorgu çalışıyor” demek, optimizasyon olduğu anlamına gelmez. Eğer aynı veriyi 100 kez çağırıyorsanız, sorgu tek başına hızlı olabilir ama toplam işyükü yıkıcıdır.
💡 Best Practice: N+1 şapkası takıp, SQL planını herkesin görebileceği şekilde okuyun; bağlantı havuzunu doğru boyutlayın; latency kaynaklarını ağ, DB ve ORM katmanında ayrı ayrı ayırın.
KAVRAMSAL TEMEL (Nedir?)

WinDbg, SOS, dump, plan okuma; bunlar “kırmızı alarm” değil, “gitmek gereken yolda ışık” tır.

Bir uygulama çöktüğünde, sistemin “deli gibi çalıştığı” anlarda tüm izler kaybolur. Dump, hangisinin bozulduğunu görmek için geri dönüş noktasıdır. SQL sorgu planları ise “neden geriye dönmüyor?” sorusunun en eski ve en doğru cevabıdır.

SQL Profiler ve Execution Plan

  • Index Seek: hedef veriye doğru kısa yol.
  • Table Scan: bütün tabloyu tarar; büyük veride can yakar.
  • Key Lookup: index var ama ek veri erişimi gerektirir.

WinDbg + SOS

  • !analyze -v crash nedenini özetler.
  • !clrstack managed call stack görünümünü verir.
  • !threads thread state ve deadlock sinyallerini gösterir.
🔑 Terimler:
N+1

Bir ana sorgu döner, ardından her satır için ayrı bir detail sorgusu açılır. Bu, “tek istekte çoklu istek” olarak bilinir.

Index Seek

Index üzerine arama yaparak hedef satıra ulaşır; maliyet düşüktür.

Table Scan

Bütün tablo taranır; yüksek I/O maliyeti doğurur.

ARAÇ KURULUMU VE ARAYÜZ (Nasıl?)

Windows tarafında gerçek teşhis için araçları doğru yerleştirin.

1) WinDbg kurulumu

Microsoft WinDbg Preview veya WinDbg for Windows SDK üzerinden kurulum. Sonra symbol cache ayarı:

.symfix
.sympath srv*https://msdl.microsoft.com/download/symbols
.reload

Symbol server ile Microsoft kütüphanelerinin stack içindeki çözümünü açarsınız.

2) SOS extension

.loadby sos clr
!analyze -v
!clrstack
!threads
!dumpheap -stat

3) Memory dump alma

dotnet-dump veya procdump kullanılır:

dotnet-dump collect -p 1234 -o dump.dmp
procdump -ma -w  dump.dmp

Sonrasında WinDbg içersinde açılır. Acı gerçek: dump almak, problem tespitini sağlamlaştırır ama yanlış yerdeki dump alıntısı hiçbir şey çözmez.

4) SQL Profiler / SSMS Execution Plan

SSMS Tools > SQL Server Profiler veya Azure Data Studio üzerinden etkinleştirme. Execution plan’da “Actual Execution Plan” açılır. Aşağıdaki patternler önemlidir:

SELECT * FROM Products WHERE Price > 1000;
-- kötü: Clustered Index Scan
-- iyi: NonClustered Index Seek
UYGULAMA VE ANALİZ (Ne Yapıyoruz?)

RestApi üzerinde laboratuvar: hata, SQL ve ağ katmanını açığa çıkarmak

  1. Tehlikeli kodu tespit et: AuthController.LoginSql içinde raw SQL kullanılıyor. var query = "select * from users where Username = {0} and Password = {1}"; ifadesi parametredir ancak saldırı için uygun görülmektedir. Bu, güvenlik ve SQL performans açısından hem nereden bakılacağını hem de neyin yanlış olduğunu öğretir.
  2. Injection payload’ı test et: Postman JSON içindeki User Login Sql çağrısını kullan. Payload: "'; Drop table users; --a@a.com". Bu, “input dışarı çıktığı anda sistemin güvenliği bozulduğunda” neye benzediğini gösterir.
  3. SSMS/SQLite kontrolü: Bu repo SQLite kullanıyor. Hatta SQL injection örnekleri SQLite üzerinden benzetilse de kavram birebir aynıdır. Hedef: parameterized query ve prepared statement mantığı.
  4. N+1 ve ilişkilendirme senaryosu: NoteController ve User ilişkisi gibi modelde, eğer tek tek user/notes yükleniyorsa, her note için ayrı query oluşturulabilir. _context.Notes.ToList() tek başına yetmez. Üzerine Include ve projection ekle.
  5. Dump alma senaryosu: “Kırılma” için bir örnek üret: `NoteController.GetAll()` içinde int ii = i / 0; çalışma sebebiyle 500 hatası üretilir. Bu, GlobalExceptionHandler üzerinden loglanır. Özellikle `Exception` log içindeki `Request.Path`, `RemoteIpAddress`, `User` ve `ErrorId` değerleri teşhis için önemlidir.
  6. Thread ve memory kontrolü: dotnet-dump ile prosesin “uykulu” ya da “kötü durumda” olduğu görselde durum netleşir. !clrstack ile hangi thread neden kilitlenmiş bakılır.

Örnek kod: güvenli SQL

var username = userDto.Username;
var password = userDto.Password;

var user = await _context.Users
    .FirstOrDefaultAsync(u => u.Username == username && u.PasswordHash == passwordHash);

// kötü örnek:
var query = "select * from users where Username = '" + username + "' and Password = '" + password + "'";
// güvenli örnek:
var safe = _context.Users.FromSqlInterpolated($@"SELECT * FROM Users WHERE Username = {username} AND Password = {password}");

Burada amaç, filtreleme katmanında “kullanıcı girişi doğrudan string birleştirme ile SQL’e gitmesin” dersini vermektir.

Network Latency ve Connection Pooling

services.AddDbContext<ApplicationDbContext>(options =>
    options.UseSqlite(connectionString)
           .EnableDetailedErrors()
           .EnableSensitiveDataLogging());

Bağlantı havuzu, DB bağlantı açma-kapama maliyetini minimize eder. Ama yanlış konfigürasyon, çok fazla connection open/close döngüsü, ağ gecikmesi gibi sorunlara yol açar. Bu yüzden ağ, db, app katmanında ayrı ayrı izleme yapılmalıdır.

BU REPO’DA TEŞHİS SINIRI

SQL ve dump adımlarını doğru ortamda çalıştır

Bu RestApi’nin veri sağlayıcısı Microsoft.EntityFrameworkCore.Sqlite; bağlantı Data Source=restapi.db. Compose PostgreSQL başlatsa da uygulama ona bağlanmaz. Mevcut repo için SQLite sorgu logları ve EF Core komutları kullanılmalıdır.

Güvenlik sınırı: SQL injection payload’ını çalıştırmayın. String birleştirme yerine LINQ parametreleştirmesinin SQL logundaki farkını gözlemleyin.

SONUÇ VE BEST PRACTICE

İsabetli teşhis, hızlı çözümün anahtarıdır.

💡 Best Practice:
  • SQL’de plan okuma alışkanlığı geliştirin: Seek vs Scan, index, key lookup.
  • ORM içinde N+1’i “include + projection + batching” ile kırın.
  • Dump alma prosedürünü hazır tutun; “on call” zorlandığında bu tekniğin ne işe yaradığını bilin.
  • Connection pooling, network latency ve application thread state’i ayrı ayrı izleyin.
⚠️ Dikkat / Uyarı: Dump almak için prosesin canlı çalıştığı sürede “sıfır üretim analizi” yapmayın. Dump alırken process donabilir, stack kaybolabilir; bunun için uygun saat ve süreç planlaması gerekir.

Öğrenilen altın kurallar

  1. Hata üzerinde çökmek yerine, hangi katmanda bozulduğunu ayırın.
  2. Plan okumadan sorguyu optimize etmeyin.
  3. “Hızlı fix” yerine, sorunun kök nedenine inin.
  4. Dump ve stack, debug’in “ölüme rağmen konuşan” kanıtı olur.
