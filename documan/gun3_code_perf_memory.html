SEKTÖREL BAKIŞ (Neden?)

Yavaş kod, aslında hafıza kaybı ve yanlış JIT davranışının ekonomik bir tezahürüdür.

Uygulama “çok yavaş” diye görülmeye başlandığında en büyük hata, sadece HTTP katmanına bakmaktır. gerçek sorun bazen String concatenation, LINQ’i büyütme, tekrar eden allocations, yanlış boxing, kayıt başına gereksiz veri taşıma ve yanlış GC davranışıdır.

Gen0Hafıza üretimi ve temizliği için kısa ömürlü nesneler.
Gen1Orta yaşama sahip nesneler; GC sürekliliği için kritik.
Gen2Uzun ömürlü nesneler; genelde yüksek maliyete gider.
⚠️ Dikkat: Kodun hızlı görünmesi için JIT warmup şarttır. Benchmark yapmadan “bir örnek rüzgar şahitliği” ile karar vermeyin. Aynı kod p50, p95, allocasyon ve GC etkisi farklı olabilir.
💡 Best Practice: Mikro benchmark yaparken benchmark runner’ın warmup, iteration, iclassify gibi davranışlarını doğru okuyun. Performans bir gecelik hatırdan değil, gerçek ölçümlerden gelir.
KAVRAMSAL TEMEL (Nedir?)

BenchmarkDotNet, Visual Studio Profiler ve memory leak anlayışı; kodun gölgesinde yürüyen “ölümsüz sorun” çözümleridir.

Yazılım mühendisliği, mobil uygulama performansını değil, “ekonomi” olarak görür: her ek nesne, her exra allocation, her string üretilmesi bir maliyet demektir. İyi mühendis, kodu değil, maliyeti optimizesini bilir.

BenchmarkDotNet

  • Runtime, JIT, allocations, throughput birlikte görünür.
  • Warmup dönemi gerekir; ilk çalıştırmalar yalancı olabilir.
  • Doğru benchmark için stable environment şarttır.

VS Profiler

  • CPU Usage ; hotspot tespitinde çok güçlüdür.
  • Memory Usage ; allocation ve retention görür.
  • Snapshot ; hangi method’un ne kadar allocation ürettiğini gösterir.
🔑 Terimler:
JIT Warmup

JIT’in ilk çalıştırma sürecinde optimize ettiği ve kodun gerçek performans profilini göstermeden önce kısa bir ısınıp-çalışması gerekir.

Allocation

Heap’e çıkartılan yeni nesneler; yüksek allocation, GC’yi sıkıştırır ve latency’i yükseltir.

Promotion

Gen0’dan Gen1 veya Gen2’ye yükselme, GC baskısını ve gecikmeyi artırır.

ARAÇ KURULUMU VE ARAYÜZ (Nasıl?)

Ölçüm için araçları kurup, doğru menü ve komutları açın.

1) BenchmarkDotNet kurulumu

dotnet add package BenchmarkDotNet
using BenchmarkDotNet.Attributes;
using BenchmarkDotNet.Running;

[MemoryDiagnoser]
public class StringBenchmarks
{
    [Benchmark]
    public string StringPlus()
    {
        var value = "A" + "B" + "C";
        return value;
    }

    [Benchmark]
    public string StringBuilderJoin()
    {
        var sb = new StringBuilder();
        sb.Append("A"); sb.Append("B"); sb.Append("C");
        return sb.ToString();
    }
}

BenchmarkRunner.Run<StringBenchmarks>();

2) Visual Studio Profiler

Arayüz: Debug > Performance Profiler... veya Debug > Start Diagnostic Tools Without Debugging

  • CPU Usage → hotspot bulur.
  • Memory Usage → allocasyon ve heap artışı izlenir.
  • Snapshot → bir anda hangi object’lerin heap’te kaldığını görür.

3) .NET Counters / Trace

dotnet-counters monitor --process-id 1234 --counters System.Runtime

dotnet-trace collect --process-id 1234 --format speedscope --output perf.trace

Bu araçlar, profilleme sırasında “hot method” ve GC davranışını anlamak için çok değerlidir.

UYGULAMA VE ANALİZ (Ne Yapıyoruz?)

Adım adım laboratuvar: gerçek kod üzerinden ölçek ve hafıza farkını çözmek

  1. Benchmark’i hazırlayın: Basit ama temsilî kod örneği yazın: string concatenation, LINQ tekrar eden enumeration, büyük list create, deserialization örnekleri.
  2. JIT ısınma sürecini anlayın: Benchmark ilk çalıştırma “bariz hızlı” görünebilir. Warmup ve iteration sayısını doğru ayarlayın. BenchmarkDotNet bunu otomatik yapar ama sen mantığı kavramalısın.
  3. CPU Usage ile hotspot bulun: Visual Studio’da Debug > Performance Profiler > CPU Usage akışı ile servis veya örnek fonksiyon çalıştırılır. Hangi method en çok CPU kullanıyor? Goruntule.
  4. Memory Usage ile allocation örneğini görün: Tekrar eden new object() veya büyük string/byte[] üretimi, heap artışını yaratır. Allocation snapshotı ile “neden GC arada patlıyor?” görülür.
  5. Memory leak kontrolü: Static list, event subscription, long-lived cache, unbounded dictionary bu türe örnektir. Özellikle WinForms/WPF gibi UI or environment, static event subscriptions can leak. In API, singleton cache misconfig is common.
  6. Gen0/Gen1/Gen2 promosyonu: Heap profile’da hangi nesnelerin kısa süre sonra Gen2’ye geçtiğini görün. Burada amaç, “her şey ayrı ayrı işlenmiyor; GC performansı” sorusunu çözmektir.

Örnek micro-benchmark

[MemoryDiagnoser]
public class ApiPayloadBench
{
    private readonly List<Product> _products = Enumerable.Range(1, 10000)
        .Select(i => new Product { Id = i, Name = $"P{i}", Price = i * 10 })
        .ToList();

    [Benchmark]
    public int SumByLoop()
    {
        var total = 0;
        foreach (var p in _products)
            total += p.Price;
        return total;
    }

    [Benchmark]
    public int SumByLinq()
    {
        return _products.Sum(p => p.Price);
    }
}

Bu örnek, “aynı iş ama farklı allocation ve CPU davranışı” farkını gösterir. Çünkü LINQ ve foreach aynı görünse de JIT ve enumerator sürümü farklı olabilir.

BU REPO’DA PERFORMANS LABORATUVARI

Ölçümün sınırını bil, sonra optimize et

RestApi.csproj şu anda BenchmarkDotNet veya profiler paketleri içermez. Benchmark sınıfını ayrı bir console/benchmark projesinde çalıştırmak, API’yi ölçüm koduyla kirletmemek için daha doğrudur. API tarafında ölçülecek gerçek yüzeyler ProductController.GetAll(), NoteController.GetAll() ve login sırasında yapılan kullanıcı sorgusudur.

Beklenen hipotez: Büyük tabloda ToList() ile tüm kayıtları taşımak allocation ve response süresini artırabilir. İlk düzeltme projection, pagination ve uygun index önerisini ölçerek doğrulamaktır; tahmin doğrudan “optimizasyon” değildir.

Benchmark akışı

dotnet new console -n RestApi.Benchmarks ile ayrı proje oluşturun, BenchmarkDotNet ekleyin ve dotnet run -c Release ile ölçün. Visual Studio Profiler’da API için CPU Usage ve Memory Usage araçlarını açın.

Snapshot’ı tek başına leak kanıtı saymayın: aynı nesnenin iki snapshot arasında tutulduğunu ve kök referansını doğrulayın.

SONUÇ VE BEST PRACTICE

Optimizasyon derken “daha hızlı” değil, “akıllıca harcanan kaynak” öğreniyorsunuz.

💡 Best Practice:
  • Performans bir teori değil, benchmark ve profiler ile ispatlanan olgudur.
  • Allocation, promotion ve GC davranışı her zaman CPU latency ile birlikte yorumlanmalıdır.
  • Memory leak için static, cache, long-lived object, event handler ve singleton kullanımına dikkat edin.
  • Özellikle API ekosisteminde, dönen object’lerin gereksiz alan kaplamadan serialize edilmesi önemlidir.
⚠️ Dikkat / Uyarı: “Hafıza az” diye optimized kod yazmak anlamına gelmez. Gereksiz derecede sıkı optimization, bakımı daha zor ve hata eğilimli kod üretir. Ölçüm ve hızlı tartışma, sonra fix edin.

Öğrenilen altın kurallar

  1. Benchmark öncesinde issue tanımla: CPU, memory, throughput, latency hangisi?
  2. Mikro benchmark ile JIT warmup ve allocation pattern’i okuyun.
  3. VS Profiler ile hotspot ve Gen0/Gen1/Gen2 davranışlarını görselleştirin.
  4. Memory leak ve atıl allocation’ları sadece “üstte görülen hata değil, sistemin temel nidası” olarak okuyun.
