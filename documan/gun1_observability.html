SEKTÖREL BAKIŞ (Neden?)

İnternet çöktüğünde “neden” sorusunu doğru cevaplamazsanız, sisteminizi kurtaramazsınız.

Latans, throughput ve error rate; işin özünü anlatır. Bir Black Friday spike sırasında 250 ms üstüne çıkan latans, 1.2 saniyelere çıkan API yanıtları ve %8’e yükselen hata oranı, sadece teknik bir sorun değil, gelir kaybı, müşteri kaybı ve operasyonel kaosu doğurur.

120–300 ms Hedeflatans eşiği; üstünde iyileştirme gerektirir.
RPS Throughput, servislerin iş yükü altında taşıma kapasitesini gösterir.
%0.1–1% Genelde kabul edilebilir hata oranı bandı; üstüne çıkarsa olay yönetimi başlar.
⚠️ Dikkat: “Sistem yavaş” demek yeterli değildir. Hangi metrik bozuldu? Hangi endpoint? Hangi kullanıcı segmenti? Üretimde bunu bilmiyorsanız, kendi başına kör bir yumurta tavada kalırsınız.
💡 Best Practice: Her servis için SLO/SLA tanımla: p95 latency, error rate, saturation. Bunu net ölçmeden performans çabası kördür.

Bu projedeki gerçek örnek

Bu repo’da Program.cs içinde global rate limiting tanımlı. AuthController.Login JWT üretimi, GlobalMiddleware her istek için kullanıcı/IP/URL bilgisi logluyor. Bu, “görünürlük” için temel örneklerdir. Ayrıca NoteController.GetAll() içinde int ii = i / 0; çalışması, olay esnasında “hata oranı” ve “structured logging” neden kritik olduğunu gösterir.

KAVRAMSAL TEMEL (Nedir?)

Latency, Throughput ve Error Rate; üç olgunun hikâyesi

Bir otobüs terminalini düşünün. Latency, bir yolcunun terminale girişten otobüse binmesine kadar geçen süre; throughput, terminalin saatlik taşıma kapasitesi; error rate ise yolcuların “yolculuk sırasında” kaybedilen ya da geri dönen kısmıdır.

Latency

  • “Cevap ne kadar sürede döndü?”
  • 客户端 p50 / p95 / p99 ölçülür.
  • Özellikle bankacılık, e-ticaret, checkout akışları için hayatta kalma-kriteridir.

Throughput

  • “Servis bir saniyede kaç istek kaldırabilir?”
  • RPS, TPS, QPS gibi metriklerle anlam kazanır.
  • Tepe yükte kapasite planlaması için olmazsa olmazdır.
🔑 Terimler:
Latency

İstekten yanıtın alınmasına kadar geçen süre. Aşırı yük altında p95 ve p99 değerleri çok daha kritik hale gelir.

Throughput

Birim zamanda işlenen istek sayısı. Sistem tasarımında kapasite ve ölçeklenebilirlik için temel göstergedir.

Error rate

Başarısız istek oranı. 5xx, timeout, retry, validation fail gibi olayları kapsar.

Bu repo’de neden önemli?

Bu API’de güçlü örnekler var: login endpoinitleri, rate limit, global exception handler, JWT güvenlik katmanı ve note/product auth separation. Bütün bunlar “görünürlük” ve “kontrol” için temel alanları açar.

ARAÇ KURULUMU VE ARAYÜZ (Nasıl?)

İzlemeyi “sadece log yazmak” sanmayın. Metrik ve trace ile akışa bakın.

1) .NET için OpenTelemetry kurulumu

dotnet add package OpenTelemetry.Extensions.Hosting
                dotnet add package OpenTelemetry.Exporter.OpenTelemetryProtocol
                dotnet add package OpenTelemetry.Instrumentation.AspNetCore
                dotnet add package OpenTelemetry.Instrumentation.Http
                dotnet add package OpenTelemetry.Instrumentation.SqlClient
                dotnet add package OpenTelemetry.Exporter.Jaeger
using OpenTelemetry.Metrics;
using OpenTelemetry.Resources;
using OpenTelemetry.Trace;

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddOpenTelemetry()
    .ConfigureResource(resource => resource
        .AddService(serviceName: "RestApi"))
    .WithTracing(tracing => tracing
        .AddAspNetCoreInstrumentation()
        .AddHttpClientInstrumentation()
        .AddSqlClientInstrumentation()
        .AddJaegerExporter(options =>
        {
            options.AgentHost = "localhost";
            options.AgentPort = 6831;
        }))
    .WithMetrics(metrics => metrics
        .AddAspNetCoreInstrumentation()
        .AddRuntimeInstrumentation());

2) Jaeger UI kurulumu

Docker ile hızlı kurulum:

  -e COLLECTOR_ZIPKIN_HOST_PORT=:9411 \
  -p 16686:16686 \

  jaegertracing/all-in-one:1.57

Arayüz: http://localhost:16686 → “Search” → “RestApi” servisini seç.

3) Serilog ile structured logging

dotnet add package Serilog.AspNetCore
dotnet add package Serilog.Sinks.Console
dotnet add package Serilog.Sinks.File
using Serilog;

Log.Logger = new LoggerConfiguration()
    .Enrich.FromLogContext()
    .Enrich.WithProperty("Service", "RestApi")
    .WriteTo.Console(outputTemplate: "[{Timestamp:HH:mm:ss} {Level:u3}] {Message:lj} | {RequestPath} | {UserName}{NewLine}{Exception}")
    .WriteTo.File("logs/restapi-.txt", rollingInterval: RollingInterval.Day)
    .CreateLogger();

builder.Host.UseSerilog();

4) .NET Runtime metrikleri

CLI: dotnet-counters monitor --process-id <PID> ve dotnet-trace collect --process-id <PID> --format speedscope.

⚠️ Dikkat / Uyarı: “Çalışıyor” diye üretimdeki sistemin sağlıklı olduğu söylenmez. İş yükünü simüle etmek, doğru metrikleri toplamak ve p95’i okuma yeteneği şarttır. Özellikle GC çoklu-thread dağılımı, gen0/gen1/gen2 gibi kavramlar günlük operasyonel kararın anahtarıdır.
UYGULAMA VE ANALİZ (Ne Yapıyoruz?)

Adım adım laboratuvar: RestApi üzerinden gerçek kullanım senaryoları

  1. İş yükünü başlat: Projeyi çalıştır. dotnet run --project RestApi/RestApi.csproj.
  2. Önce endpointleri tanı: Bu repo içinde AuthController, NoteController, ProductController üç ana domain akışı sunuyor. Postman JSON dosyası içindeki User Login, User Register, Product Add akışlarını tanı.
  3. Jaeger ile bir trace oluştur: Örnek: POST /api/auth/login çağrısı sonrası JWT production ve user lookup işlemini takip et. Gözün trace içindeki span’lara takılsın.
  4. Structured log üret: GlobalMiddleware içinde mevcut `Console.WriteLine` tarzı log değil, structured log kullan. Kullanıcı, IP, URL, User-Agent, timestamp, operationName ekle.
  5. dotnet-counters ile canlı izleme: dotnet-counters monitor --process-id $(pgrep -f RestApi) ardından System.Runtime sekmesinde CPU, GC Heap Size, Gen0/Gen1/Gen2 gözetimini izle.
  6. dotnet-trace ile profil: dotnet-trace collect --process-id $(pgrep -f RestApi) --format speedscope --output restapi.trace Çıktıdan “hot path” ve çağrı zincirini gör.
  7. Rastgele yük simülasyonu: 20–50 saniyelik concurrency artışı ile api/product ve api/note üzerinden aşırı yük uygula. Latency değişimlerini izleme ekranında not al.

Analiz soruları

  • İsteklerin p95’si ne kadar?
  • Hangi endpoint en çok CPU tüketiyor?
  • Hangi sırada Graph/Trace bir “slow span” üretiyor?
  • GC heap artışı kaç saniyede ve hangi çalıştırmada ortaya çıkıyor?

SONUÇ VE BEST PRACTICE

“İyi görünürlük” bir araç değil; organizasyon kültürüdür.

💡 Best Practice:
  • Her servisin tekil SLO’su olsun: latency, throughput, error rate.
  • Structured logging şart: requestId, userId, tenantId, traceId, spanId.
  • OpenTelemetry + Jaeger + .NET Runtime metric kombinasyonu üretim için vazgeçilmez bir katmandır.
  • Trace ve log id’lerini korelasyon için kullan; tozlu “başarısız bir örnek” kalmaz.
⚠️ Dikkat / Uyarı: Sadece log dosyasına bakmak yetmez. Hata ve latans sinyallerini, CPU, memory, GC ve ağ katmanı ile birleştirmeniz gerekir. Birim iş yükleri altında bile p95 örnekleri tehlikeli olabilir. Ölçüm yapmadan, “geliştirme ortamında iyi” diye üretime güvenmeyin.

Öğrenilen altın kurallar

  1. İlk iş: doğru metriği seçmek.
  2. İkinci iş: sistemin gerçek iş yükünü simüle etmek.
  3. Üçüncü iş: p95 ve error rate’i birlikte yorumlamak.
  4. Dördüncü iş: kaynak tüketimini “sadece CPU” değil, GC ve thread pool ile okumak.
